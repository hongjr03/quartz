## 摘要

追踪（tracing）和引用计数（reference counting）一直被视为两种截然不同的垃圾回收方法，具有迥异的性能特征。我们分别实现了两种类型的高性能回收器，在此过程中观察到：对它们优化得越多，它们的行为就越相似——它们似乎共享某种深层结构。

我们提出了这两种算法的形式化表述，表明它们实际上互为对偶。直观上，区别在于追踪操作的是活对象（"物质"），而引用计数操作的是死对象（"反物质"）。追踪回收器执行的每一个操作，在引用计数回收器中都有一个精确对应的"反操作"。

借助这一框架，我们证明所有高性能回收器（例如延迟引用计数和分代回收）实际上都是追踪与引用计数的混合体。我们建立了一个统一的成本模型来量化选择不同混合比例所带来的权衡。这使得我们可以根据系统性能需求和目标应用的预期特征，选择正确的方案。

## 1. 引言

到1960年，两种最基本的存储回收方法——追踪 [^33] 和引用计数 [^18]——都已问世。

此后在这两个范式中都涌现了大量进展。追踪方面的主要进展包括：迭代复制回收 [^15]、分代回收 [^41][^1]、常量空间追踪 [^36]、屏障优化技术 [^13][^45][^46]、软实时回收 [^2][^7][^8][^14][^26][^30][^44]、硬实时回收 [^5][^16][^23]、分布式垃圾回收 [^29]、复制型复制回收 [^34] 以及多处理器并发回收 [^21][^22][^27][^28][^39]。

引用计数方面的主要进展包括：增量释放 [^42]、延迟引用计数 [^20]、循环回收 [^17][^32][^6]、编译时消除计数操作 [^9] 以及多处理器并发回收 [^3][^19][^31]。

然而，所有这些进展都只是对这两种在高级语言诞生之初便已奠定的基本方法的细化。

追踪和引用计数历来被视为两种不同的存储回收方法。我们实现了两种类型的回收器：一个多处理器并发引用计数回收器（含循环回收）[^3][^6] 和一个单处理器实时增量追踪回收器 [^4][^5]。在这一过程中，我们发现这两种方法之间有一些惊人的相似之处。特别是，当对朴素算法进行了大幅优化之后，它们所面临的难题出奇地相似。这让我们推测，这两种算法实际上共享某种"深层结构"。

在本文中，我们证明这两种基本的存储回收方法——追踪和引用计数——互为**算法对偶**（algorithmic duals）。直观上，可以将追踪理解为操作活对象即"物质"，而引用计数操作死对象即"反物质"。追踪回收器执行的每一个操作，引用计数回收器都有一个对应的"反操作"。

以这种方式来看待这两种算法，为理解其中的权衡、潜在的优化策略，以及在统一的存储回收框架中结合引用计数与追踪的可能性，提供了全新的视角。

我们首先对追踪和引用计数进行定性比较（第2节），然后证明这两种算法事实上互为对偶（第3节）。接着我们证明，所有实际使用的高性能回收器，本质上都是结合了追踪和引用计数的混合体（第4节）。随后我们讨论循环回收的问题（第5节），并将框架扩展到具有任意数量独立堆的回收器（第6节）。基于我们的回收器分类法，我们提出了一个统一的成本模型，可以直接比较各种回收器的性能特征（第7节）。然后我们讨论在回收器实现中可以做出的空间-时间权衡（第8节）。最后给出结论。

## 2. 定性比较

我们首先对追踪和引用计数回收器之间的差异进行定性比较，并讨论随着优化的施加，这两种算法如何变得越来越相似。

### 2.1 截然相反？

追踪和引用计数的朴素实现在许多方面大相径庭。最常被引用的差异如图所示：

<figure>

|  | 追踪 | 引用计数 |
|---|---|---|
| 回收模式 | 批量 | 增量 |
| 每次变异的代价 | 无 | 高 |
| 吞吐量 | 高 | 低 |
| 暂停时间 | 长 | 短 |
| 实时性 | 否 | 是 |
| 回收循环 | 是 | 否 |

<figcaption>图 1：追踪与引用计数对比（Tracing vs. Reference Counting）</figcaption>
</figure>

引用计数天然是增量的，因为它在每次指针写入时都更新引用计数；追踪则以"批量模式"运行，需要一次性扫描整个堆。追踪不会为指针变更付出任何代价，而引用计数则代价高昂——每次指针写入（包括向栈帧的写入）都会触发引用计数更新。追踪回收器的吞吐量相应地更高。

另一方面，引用计数回收器的暂停时间极短，这使其天然适用于实时应用。

最后，追踪能够回收循环垃圾，而引用计数不能。因此，当引用计数应用于可能包含循环垃圾的堆时，循环要么必须通过备用追踪回收器来回收 [^43]，要么通过试探删除（trial deletion）算法来回收 [^6][^17][^32]。

### 2.2 趋同

我们对追踪和引用计数相似性的探究始于一个现象：随着我们对引用计数和追踪回收器不断优化，它们开始越来越多地呈现对方的特点。

引用计数的增量性质通常被视为其根本优势。然而，每次将新指针加载到寄存器时都更新引用计数的代价，对于高性能应用来说通常过高。因此，大多数高性能引用计数实现都采用某种形式的**延迟引用计数**（deferred reference counting）[^20]，其中来自栈帧的引用被单独处理 [^3][^19]。

但这意味着，当一个对象的引用计数降为零时，它不能被立即回收，因为它可能还存在来自栈的引用（未被计入）。因此，回收被推迟到栈引用的周期性扫描进行时。而这带来的后果是延迟回收、浮动垃圾和更长的应用暂停时间——正是追踪回收器的典型特征！

现在再来看一个高性能追踪回收器的实现：它的两个基本优势是无需为每次变更付出代价，以及天然能够回收循环垃圾。然而，追踪的一个基本劣势是死对象的释放被推迟到回收周期结束时，导致对象回收延迟和长暂停时间。

通常施加于追踪回收器的第一个优化是**分代回收**（generational collection）[^41]。这降低了平均暂停时间和对象回收的延迟，但同时引入了每次变更的代价——从而兼具了引用计数回收的某些优点和缺点。

进一步尝试精确限制暂停时间的尝试体现在**Train 算法** [^25] 中，它将内存划分为固定大小的 car，并将 car 编组成 train。每次回收一个 car，从而实现确定性的暂停时间（除非存在热门对象）。此外，跨 car 的循环可能导致病态行为。而在循环面前表现异常，恰恰是引用计数的标志性特征！

## 3. 算法对偶

我们亲身经历（并深感挫败）了优化后的引用计数和追踪回收器趋向一致的现象，这直接促使我们对这两种算法进行更深入的研究，以期找到实践中似乎显现的那些基本相似性。

### 3.1 物质 vs. 反物质

要看清两种算法之间的联系，需要以一种稍有不同的方式来看待它们。首先，我们考虑一种引用计数的变体，其中递减操作被批处理并在"回收时刻"执行，而不是立即执行（这可以视为一种后续优化）。其次，我们考虑一种追踪的变体，其中追踪过程重建每个对象的实际引用计数，而不仅仅是设置标记位（标记位可以视为一种后续优化，将引用计数压缩为 1 位的"粘滞"引用计数）。

从这个角度看，两种算法之间的平行关系非常惊人，总结如下：

<figure>

|  | 追踪 | 引用计数 |
|---|---|---|
| 起始点 | 根（roots） | 反根（anti-roots） |
| 图遍历 | 从根向前 | 从反根向前 |
| 遍历的对象 | 活的 | 死的 |
| 初始 RC | 低（0） | 高 |
| RC 重建 | 递增 | 递减 |
| 额外迭代 | 清除（sweep）阶段 | 试探删除 |

<figcaption>图 2：追踪与引用计数再比较（Tracing vs. Reference Counting, Revisited）</figcaption>
</figure>

追踪垃圾回收从根开始向前遍历对象图，以找到活数据。引用计数从**反根**（引用计数被递减至零的对象集合）开始向前遍历对象图，以找到死数据。

直观上，可以将追踪理解为操作"物质"，而引用计数操作"反物质"。形式上说，在没有循环的情况下，引用计数计算的是追踪的**图补集**。

追踪将对象的引用计数初始化为零，在图遍历过程中递增它们，直到达到真正的引用计数。引用计数将引用计数"初始化"为一个超出真实值的数，在图遍历过程中递减它们，直到达到真正的引用计数（忽略循环的存在）。

引用计数必须执行额外的图迭代以完成循环数据的回收。这通常被视为引用计数的主要缺点。

但追踪也必须执行额外的迭代，而且是在整个对象空间上：那就是清除（sweep）阶段，回收引用计数为零（标记位清除）的对象。虽然半空间复制回收器通过仅复制活数据来避免这一时间开销，但这本质上是一种简单的线性空间-时间权衡：以线性的空间代价换取省去一次线性遍历。

### 3.2 不动点形式化

我们首先抽象地描述垃圾回收算法，然后将其细化为追踪和引用计数对偶。

贯穿本文，我们假设所有内存由固定大小的对象组成，因此忽略碎片问题 [^4]。

我们形式化地刻画系统内存：

- $V$ 是对象图中的顶点集。$V$ 是所有对象的全集，既包括垃圾也包括"空闲列表"中的对象。$V$ 并不包含全部内存，因为回收器还必须维护元数据以支持回收。
- $E$ 是图中边的多重集（一个节点可以有多个指向同一节点的指针）。
- $R$（其中 $R^{\odot} \subseteq V$）是图的根的多重集（位于栈帧和全局变量中）。
- $V_F \subseteq V$ 是"空闲列表"，已知可供分配的顶点集。
- $V_L = R^{\star}$ 是对象图中的活顶点集：从根可达的顶点集。
- $E_L = \{ (x, y) : x \in V_L \}$ 是对象图中的活边集。
- $V_D = V - V_L$ 是死顶点集。一般 $V_F \subseteq V_D$，但贯穿本文我们假设只有当 $V_F = \varnothing$ 时才触发回收。
- $V_C \subseteq V_D$ 是循环垃圾顶点集；即它们不在 $V_L$ 中，但在图中均有入边。
- $\rho(v)$（$v \in V$）是回收器计算出的顶点 $v$ 的引用计数。

对象图是三元组 $G = \langle V, E, R \rangle$。

垃圾回收可以表达为一个不动点计算。为顶点 $v \in V$ 计算引用计数 $\rho(v)$ 的指派，其中引用计数包括来自根集 $R$ 的贡献和来自具有非零引用计数的顶点的入边贡献：

$$
\rho(x) = \bigl| [ x : x \in R ] \bigr| + \bigl| [ (w, x) : (w, x) \in E \land \rho(w) > 0 ] \bigr| \tag{1}
$$

一旦引用计数被指派，引用计数为零的顶点被回收：

$$
V_F = [ v \in V : \rho(v) = 0 ] \tag{2}
$$

一般而言，对于给定的对象图可能存在多个这样的不动点。例如，考虑 $V = \{a, b\}$，$R = \emptyset$ 且 $E = \{(a,b), (b,a)\}$ 的情况。那么 $\rho(a)=\rho(b)=0$ 和 $\rho(a)=\rho(b)=1$ 是方程的两个可能不动点。前者是**最小不动点**，后者是**最大不动点**。显然，我们希望回收最小不动点所标识的垃圾。

不动点形式化本身并不是一种算法。我们现在来考察垃圾回收算法给出的解。

### 3.3 追踪垃圾回收

真实算法操作上述定义的对象图 $G$。此外，它们维护：

- $W$，算法待处理对象的工作列表。当 $W$ 为空时，算法终止。

追踪垃圾回收算法如下：

```
collect-by-tracing()
  initialize-for-tracing(W)
  scan-by-tracing(W)
  sweep-for-tracing()

scan-by-tracing(W)
  while W ≠ ∅
    remove w from W
    ρ(w) ← ρ(w) + 1
    if ρ(w) = 1
      for each x ∈ [v : (w, v) ∈ E]
        W ← W ⨄ [x]

sweep-for-tracing()
  for each v ∈ V
    if ρ(v) = 0
      V_F ← V_F ∪ {v}
    ρ(v) ← 0

new(x)
  ρ(x) ← 0

initialize-for-tracing(W)
  W ← find-roots()
<figure>
```

<figcaption>图 3(b)：追踪垃圾回收算法。注意在扫描和回收方法上与图 4 引用计数算法的精确对应关系。</figcaption>
</figure>

初始时，所有顶点的引用计数均为零，要么是因为 `new()` 创建时如此，要么是在上一次 `sweep-for-tracing()` 中被重置为零。`initialize-for-tracing()` 函数将工作列表初始化为根集 $R$。

算法的核心是 `scan-by-tracing()` 函数，它重建每个顶点的引用计数。它从工作列表的每个元素向前扫描，递增其遇到的顶点的引用计数。当首次遇到顶点 $w$（$\rho(w)=1$）时，它通过将该顶点的所有出边加入工作列表 $W$ 来递归处理。

当 while 循环终止时，它已经发现了 $R^{\star}$ 中的所有节点——即所有活节点 $V_L$——并将它们的引用计数设置为 $E_L$ 中相应的入边数。

最后，调用 `sweep-for-tracing()` 将未使用的顶点返还给空闲存储 $V_F$，并将引用计数重置为零，为下一次回收做准备。

该算法与标准追踪回收器之间唯一实质性的区别在于，我们维护完整的引用计数，而不是一个布尔标志来表示顶点是否已被访问。但这不改变算法的复杂度（尽管在实践中会影响运行时间）。如前所述，标记"位"可以视为一个退化的引用计数，它在 1 处"粘滞"。

追踪垃圾回收计算方程 (1) 的**最小不动点**。

### 3.4 引用计数垃圾回收

引用计数垃圾回收算法在结构上与追踪算法完全对应。引用计数算法的这种表述有些不寻常之处，即递减操作被缓冲而不是立即执行。我们并非提倡以此作为实现方式，而是作为理解两种算法之间关系的一种方法。延迟递减操作在时间上平移了部分工作，但不影响算法的复杂度。

```
collect-by-counting(W)
  scan-by-counting(W)
  sweep-for-counting()

scan-by-counting(W)
  while W ≠ ∅
    remove w from W
    ρ(w) ← ρ(w) - 1
    if ρ(w) = 0
      for each x ∈ [v : (w, v) ∈ E]
        W ← W ⨄ [x]

sweep-for-counting()
  for each v ∈ V
    if ρ(v) = 0
      V_F ← V_F ∪ {v}

new(x)
  ρ(x) ← 0

dec(x)
  W ← W ⨄ [x]

inc(x)
  ρ(x) ← ρ(x) + 1

assign(a, p)
  l ← [a]
  [a] ← p
  dec(l)
  inc(p)
<figure>
```

</figure>

<figure>
  <img src="gc/images/bacon-fig4a.jpg" loading="lazy" alt="图 4(a)：引用计数回收器结构——根到堆及堆内均引用计数">

因此，`dec()` 函数将顶点加入工作列表 $W$，而不是由初始化函数来加入。

在变更时，当指针被存储到内存中，`assign` 函数被调用，它接受待存储的指针 $p$ 和存储目标地址 $a$。该函数加载地址 $a$ 处的旧引用目标 $l$，并调用 `dec(l)` 将 $l$ 加入工作列表 $W$。地址被更新，新引用目标 $p$ 的引用计数通过 `inc(p)` 递增。

当回收被触发时，所有的递增操作已经执行，但自上次回收以来的递减操作尚未执行；它们已被记录在 $W$ 中。因此，在扫描函数开始时，引用计数是对真实计数的**高估**。

与追踪回收一样，算法的核心是扫描阶段，由 `scan-by-counting()` 函数在回收时刻执行。该算法从工作列表的每个元素向前扫描，递减其遇到的顶点的引用计数。当发现一个垃圾顶点 $w$（$\rho(w)=0$）时，它通过将该顶点的所有边加入工作列表 $W$ 来递归处理。最后，调用 `sweep-for-counting()` 将未使用的顶点返还给空闲存储。

当将两个算法并排对比时，它们之间的关系显而易见。扫描函数完全相同，唯一的区别在于追踪中使用引用计数递增，而引用计数中使用引用计数递减，以及递归条件分别检查引用计数是否为 1（追踪）或 0（引用计数）。改变算法核心中的两个字符，我们就从追踪切换到了引用计数！

另一个有趣的区别是，`sweep-for-counting()` 函数不会将引用计数重置为零。

从这个角度看，追踪和引用计数算法共享相同的基本结构。唯一区别在于，追踪从引用计数的**低估**开始，通过在追踪过程中遇到顶点时递增计数来收敛到真实值。而引用计数从**高估**开始（因为有来自实际上已不再活着的对象的计数入边），通过处理递减操作来收敛到真实的引用计数。

换个角度看，追踪计算方程 (1) 的**最小不动点**，而引用计数计算**最大不动点**。这两个解之间的集合差就是循环垃圾。

## 4. 追踪/计数混合体

鉴于我们发现追踪和引用计数在结构上的相似性，我们开始重新审视各种回收器架构，以理解这两种回收风格之间的相互作用。我们观察到，所有现实的垃圾回收器实际上都是追踪和引用计数的某种混合形式。

这解释了为什么一个优化后的"追踪回收器"和一个优化后的"引用计数回收器"会变得越来越相似：因为它们实际上正在吸收彼此的特征。

我们将看到，各种回收器之间唯一根本性的区别在于存储的划分，以及在不同划分区域中对引用计数维护责任的分配——是分配给追踪还是引用计数。在这些决策做出之后，剩下的选择都是实现细节，归结为各种空间-时间权衡，我们将在第 8 节详细讨论。

我们根据存储划分对回收器进行大致分类：**统一堆回收器**（unified heap collectors）只有一个堆；**分裂堆回收器**（split heap collectors）将内存分成两个区域，如分代回收器；**多堆回收器**（multiple heap collectors）具有两个以上的内存区域，如分布式垃圾回收器或 Train 算法 [^25]。

注意，在本文分析中，我们将半空间视为单个堆区域，因为同一时间只有一个半空间处于活动状态（我们不讨论并发回收器）。半空间的使用是第 8 节中考虑的空间-时间权衡之一。

### 4.1 延迟引用计数

延迟引用计数（DRC）回收器是一种统一堆回收器。然而，这类回收器仍然有两个存储区域，即堆 $V$ 和根 $R$。在这两个区域上追踪和引用计数的不同组合会生成不同的算法。

延迟引用计数是一种混合体，其中引用计数维护堆对象之间的计数。引用计数为零的对象被维护在零计数表（ZCT）中。

根引用不被计数。取而代之的是，在回收时，ZCT 中被根指向的任何元素都被移出 ZCT，剩余的 ZCT 条目被回收。

因为根的变更率几乎总是极高，延迟引用计数将考虑根的代价从应用程序转移到了回收器。

但检查根指针并将其引用目标移出 ZCT 的行为就是**追踪**：它是沿着指针向前并递增被发现对象引用计数的行为。

延迟引用计数的结构：从栈到堆的引用被追踪，而堆内部的引用被引用计数。

  <figcaption>图 5(a)：延迟引用计数（DRC）结构示意图</figcaption>

写屏障（`assign` 函数）被修改为过滤掉所有源不是根的指针。因此在回收时，所有堆内指针的递增操作已经执行，递减操作已被放入工作列表 $W$。

回收操作本身找到根集并递增其所有目标。然后它调用标准的引用计数回收操作（`scan-by-counting` 和 `sweep-for-counting`），后者计算引用计数然后回收引用计数为零的对象。最后，通过 `untrace-roots` 撤销根对引用计数的更新。

```
collect-by-drc(W)
  R ← find-roots()
  trace-roots(R)
  scan-by-counting(W)
  sweep-for-counting()
  untrace-roots(R)

trace-roots(R)
  for r ∈ R
    ρ(r) ← ρ(r) + 1

untrace-roots(R)
  for r ∈ R
    ρ(r) ← ρ(r) - 1

drc-assign(a, p)
  l ← [a]
  [a] ← p
  if ¬ RootPointer(a)
    dec(l)
    inc(p)

```

该算法与经典 DRC 算法的唯一区别是，我们没有显式维护 ZCT（零计数表）；通过将递减操作延迟到工作列表中，我们在对象引用计数降为零时直接发现垃圾。但这仅仅是一个实现选择。一些 DRC 回收器也采用这种替代方法 [^3]。

### 4.2 部分追踪

在统一堆中，也可以考虑实现延迟引用计数的逆操作，即对根进行引用计数而对堆进行追踪——我们称之为**部分追踪**（partial tracing）算法。它与延迟引用计数只是边的角色互换，因此与延迟引用计数之间存在对偶关系，正如追踪和引用计数本身互为对偶一样。

部分追踪算法的 `assign` 函数具有互补的过滤条件：它仅考虑根指针。对于那些指针，它调用特殊的递增和递减操作，其功能是动态维护根集。本质上，这个集合可以被视为仅为根维护的引用计数（不同于 $\rho$）。

一旦根集通过写屏障被维护好，回收就只是调用标准的追踪算法。它无需通过搜索来找到根（例如扫描栈和全局变量），只需传入它一直在维护的根集即可。

```
collect-by-partial-tracing(R)
  scan-by-tracing(R)
  sweep-for-tracing()

pt-inc(x)
  R ← R ⨄ [x]

pt-dec(x)
  R ← R - [x]

pt-assign(a, p)
  l ← [a]
  [a] ← p
  if RootPointer(a)
    pt-dec(l)
    pt-inc(p)

```

<figcaption>图 6(b)：部分追踪算法（Partial Tracing）。该算法是延迟引用计数的对偶——仅根指针被引用计数，堆通过追踪回收。</figcaption>
</figure>

这种混合方式的基本性质是：当追踪开始时，引用计数已经使某些顶点——凭借它们在集合 $R$ 中——具有非零引用计数。这些"虚拟引用计数"随后通过作为 `scan-by-tracing` 函数的工作列表输入而被具体化（materialized）。

请注意，`assign` 函数总是与混合回收器中的引用计数部分相关联，而非追踪部分。对于 DRC，堆被引用计数且屏障记录来自堆的指针。对于部分追踪，根被引用计数且屏障记录来自栈的指针。一般而言，**写屏障的存在是算法中某种引用计数式行为的标志**。

我们不知道有任何部分追踪的实现。对于语言运行时系统，它将具有出奇差的性能。它成功结合了追踪和引用计数的大部分最坏方面：如纯引用计数一般具有极高的变更代价，却一点也得不到引用计数的增量性。

然而，在其他环境中实现垃圾回收系统时（例如在磁盘、网络或昂贵的运行时结构上操作），这样的算法可能是有价值的。例如，如果写根指针的代价本来就相当高，而通过扫描找到根的代价又极其昂贵，那么对根进行引用计数可能是最佳方案。

### 4.3 分代垃圾回收

延迟引用计数展示了统一堆内的混合。我们现在考虑将堆分裂为两个区域的回收器：新生区（nursery）和成熟空间（mature space）。

分裂堆回收器实际上有三个内存区域：根、新生区和堆。所有分裂堆回收器都具有这样的性质：它们都是追踪和引用计数的某种混合形式，我们现在就来证明这一点。

分代回收器通过将对象分配到新生区，并只将新生区回收中存活下来的对象移入成熟空间，有效降低了进入成熟空间的分配速率。平均暂停时间大幅降低，吞吐量也通常得到提升。

#### 4.3.1 追踪式分代回收

最常见的分裂堆回收器架构是分代回收器 [^41]。

为了能够独立回收新生区（而不必追踪整个成熟空间），分代回收器维护一个**记忆集**（remembered set），记录被成熟空间对象指向的新生区对象。记忆集可以用位图、卡片标记或顺序存储缓冲区（SSB）来实现。

记忆集由一个写屏障维护，该写屏障在每次堆指针更新时执行。写屏障检查指针是否从成熟空间跨越到新生区，如果是，则将其加入记忆集。

到此，与前几种回收器的类比应该已经相当明显：**写屏障就是 `assign` 函数**，而我们已经观察到这与回收器中引用计数部分相关联。

记忆集实际上是非零引用计数的集合表示——是延迟引用计数中使用的零计数表（ZCT）的补集，只不过其范围被限定在新生区。正如我们所见，从非零引用计数开始是引用计数的一项基本特征。

用我们的形式化表述的分代回收算法如下：

```
gen-collect-nursery()
  gen-nursery-initialize()
  gen-nursery-scan()
  nursery-sweep()

gen-nursery-initialize()
  R ← find-roots()
  R_N ← [r : r ∈ R ∧ r ∈ V_N]
  for each r ∈ R_N
    W ← W ⨄ [r]

gen-nursery-scan()
  while W ≠ ∅
    remove w from W
    ρ(w) ← ρ(w) + 1
    if ρ(w) = 1
      for each x ∈ [v : (w, v) ∈ E]
        if x ∈ V_N
          W ← W ⨄ [x]

gen-assign(a, p)
  l ← [a]
  [a] ← p
  if InMatureSpace(a)
    gen-dec(l)
    gen-inc(p)

gen-inc(x)
  if x ∈ V_N
    W ← W ⨄ [x]

gen-dec(x)
  if x ∈ V_N
    ρ(x) ← ρ(x) - 1

gen-collect-heap()
  gen-collect-nursery()
  collect-by-tracing()

nursery-sweep()
  for each v ∈ V_N
    if ρ(v) = 0
      V_NF ← V_NF ∪ {v}
    else
      V_N ← V_N \ {v}
      V_H ← V_H ∪ {v}
      ρ(v) ← 0
<figure>
```

<figcaption>图 8：分代垃圾回收算法（Generational Garbage Collection Algorithm）。`assign` 函数只考虑从成熟空间指向新生区的指针；递减立即执行，递增被推迟并记录为追踪的根。</figcaption>
</figure>

`assign` 函数只考虑从成熟空间指向新生区的指针。递减操作立即执行，递增操作被推迟，放入工作列表。虽然这可能显得有点反直觉，但请回顾在我们的表述中，所有回收器都计算引用计数，而不仅仅是标记位。如果我们只需要标记位，则可以省略递减操作。在递增操作被记录到工作列表中的意义在于，它们形成了一组根，新生区的追踪从这组根出发进行（除了栈根之外）。

`gen-nursery-initialize` 函数取走分代写屏障创建的工作列表，并加入指向新生区的根。然后它用 `gen-nursery-scan` 函数对新生区进行追踪。该函数与基本追踪算法的 `scan-by-tracing` 函数相同（图 3），只是节点仅在位于新生区 $V_N$ 中时才被加入 $W$。

sweep 函数将引用计数非零的节点从新生区移入成熟空间，并将其引用计数设为零。这维护了一个不变式：在成熟空间回收之间，成熟空间中的所有节点引用计数均为零（追踪不变式）。

为回收整个堆（`gen-collect-heap`），先回收新生区，然后调用标准追踪回收器。新生区已知为空，因此只考虑成熟空间对象。

分代回收器的结构示意：从根集到新生区和成熟空间的引用均被追踪。

<figure>
  <img src="gc/images/bacon-fig7a.jpg" loading="lazy" alt="图 7(a)：标准分代回收——新生区和成熟空间均追踪">
  <figcaption>图 7(a)：标准分代回收——新生区与成熟空间均被追踪</figcaption>
</figure>

新生区内部和成熟空间内部的引用均被追踪。从成熟空间到新生区的引用被引用计数。最后，存在一条从新生区到成熟空间的**宏边**（macro-edge，标有"M"的箭头）。

宏边可以视为一个汇总的引用计数。由于我们不追踪从新生区到成熟空间的指针，成熟空间无法被独立回收。可能存在从新生区指向成熟空间中任意或全部对象的引用。因此，唯一安全回收成熟空间的时机是当新生区为空时，因为此时从新生区到成熟空间的引用计数已知为零。

#### 4.3.2 新生区引用计数的分代回收

我们现在可以通过考虑追踪和引用计数的不同组合来探索分代回收器的设计空间。首先考虑对新生区应用对偶方法（引用计数），而对成熟空间应用同样的方法（追踪）。

该算法对新生区执行延迟引用计数，并维护从成熟空间到新生区的引用计数。

```
rcn-collect-nursery()
  rcn-trace-roots()
  rcn-nursery-scan()
  nursery-sweep()

rcn-trace-roots()
  R ← find-roots()
  R_N ← [r : r ∈ R ∧ r ∈ V_N]
  for each r ∈ R_N
    ρ(r) ← ρ(r) + 1

rcn-nursery-scan()
  while W ≠ ∅
    remove w from W
    ρ(w) ← ρ(w) - 1
    if ρ(w) = 0
      for each x ∈ [v : (w, v) ∈ E]
        if x ∈ V_N
          W ← W ⨄ [x]

rcn-assign(a, p)
  l ← [a]
  [a] ← p
  rcn-dec(l)
  rcn-inc(p)

rcn-dec(x)
  if x ∈ V_N
    W ← W ⨄ [x]

rcn-inc(x)
  if x ∈ V_N
    ρ(x) ← ρ(x) + 1

rcn-collect-heap()
  rcn-collect-nursery()
  collect-by-tracing()
<figure>
```

<figcaption>图 9：新生区引用计数的分代回收算法（Reference Counted Nursery Collection Algorithm）。新生区采用延迟引用计数，成熟空间采用追踪。</figcaption>
</figure>

具体而言，我们对新生区应用延迟引用计数（我们不引用计数根指针进入新生区的更新）。相反，在 `rcn-collect-nursery` 开始时，我们应用与 DRC 开始时相同的操作，但限制在新生区内：我们从根追踪进入新生区，递增目标对象的引用计数。请注意，这个操作本质上与对应的追踪式新生区回收器所做的相同（将新生区根加入工作列表以供追踪）。

`rcn-nursery-scan` 函数就是 `gen-nursery-scan` 函数的引用计数对偶：它递归递减引用计数而不是递增，只不过不跨越进入成熟空间。

最后，调用与分代回收器相同的 `nursery-sweep` 函数。与 DRC 回收器不同的是，不执行 `untrace` 操作。原因是 `nursery-sweep` 将被移入成熟空间对象的引用计数设为零，从而撤销了 `rcn-trace-roots` 执行的递增操作。由于成熟空间将被追踪，所有引用计数必须从零开始，因此无需精确撤销追踪根和递增其引用计数的效果。

该回收器的优势在于循环垃圾最终会被回收，因为成熟空间会被追踪；劣势在于它对那些变更率可能最高的对象（年轻对象）进行引用计数。因此，昂贵的写屏障操作将针对最频繁的而非最不频繁的操作。

#### 4.3.3 堆引用计数的分代回收

前一种算法的问题提示了相反的方法：追踪新生区，引用计数成熟空间。

<figure>
  <img src="gc/images/bacon-fig7c.jpg" loading="lazy" alt="图 7(c)：新生区追踪 + 成熟空间引用计数（Ulterior Reference Counting）">
  <figcaption>图 7(c)：新生区追踪，成熟空间引用计数（Ulterior Reference Counting）</figcaption>
</figure>

这具有的优势是新生区中的变更不被写屏障记录，但劣势是需要为成熟空间引入额外的循环回收机制。

这种架构事实上最近由 Blackburn 和 McKinley 以 "Ulterior Reference Counting" 之名实现 [^12]。他们使用试探删除算法（见 5.3 节）来回收成熟空间中的循环。

随着我们开始探索追踪和引用计数更奇特的排列组合，这套方法论的力量变得清晰：它使我们能够轻松探索回收器架构的设计空间，并将它们清晰地相互归类。

```
urc-collect-nursery()
  urc-nursery-initialize()
  urc-nursery-scan()
  urc-nursery-sweep()

urc-nursery-initialize()
  R ← find-roots()
  R_N ← [r : r ∈ R ∧ r ∈ V_N]
  for each r ∈ R_N
    W ← W ⨄ [r]

urc-nursery-scan()
  while W ≠ ∅
    remove w from W
    ρ(w) ← ρ(w) + 1
    if ρ(w) = 1
      for each x ∈ [v : (w, v) ∈ E]
        if x ∈ V_N
          W ← W ⨄ [x]
        else
          ρ(x) ← ρ(x) + 1

urc-nursery-sweep()
  for each v ∈ V_N
    if ρ(v) = 0
      V_NF ← V_NF ∪ {v}
    else
      V_N ← V_N \ {v}
      V_H ← V_H ∪ {v}
      for each r ∈ R_N
        ρ(r) ← ρ(r) - 1

urc-assign(a, p)
  l ← [a]
  [a] ← p
  if InMatureSpace(a)
    urc-dec(l)
    urc-inc(p)

urc-dec(x)
  if x ∈ V_N
    ρ(x) ← ρ(x) - 1
  else

该算法的扫描方法与标准分代回收器（图 8）相同，增加了一项：来自新生区活对象指向成熟空间的引用必须在撤离前递增成熟空间对象的引用计数（以维护成熟空间不变式——其对象包含它们的堆引用计数）。

`nursery-sweep` 函数也与标准分代回收器的类似，不同之处在于从新生区移入成熟空间的对象，其引用计数必须减去来自根的贡献。这是因为成熟空间由延迟引用计数回收，因此我们必须再次维护 DRC 堆不变式。

`assign` 函数执行与标准分代回收器相同的写屏障，不同之处在于成熟空间内部的指针也进行引用计数：递增操作立即执行，递减操作放入成熟空间的单独工作列表。

一次完整回收首先回收新生区，此后新生区为空，成熟空间满足 DRC 不变式：每个对象的引用计数等于来自堆中对象的引用数。然后调用 DRC 算法回收成熟空间中的垃圾。

## 5. 循环回收

引用计数回收器的一个主要缺点是无法找到循环垃圾。因此，需要额外的机制。

到目前为止，我们对引用计数的考察忽略了循环。现在我们来考虑回收循环垃圾的各种方法。

有两种基本方法：备用追踪回收器，或循环回收器。我们首先在单堆回收器的上下文中介绍这些算法。

### 5.1 备用追踪回收

第一种也是最常用的一种方法是，引用计数回收器偶尔执行一次追踪回收以释放循环 [^43]。引用计数既应用于从根到堆的引用，也应用于堆内引用，但偶尔会在整个堆上使用追踪，此时它将回收引用计数遗漏的垃圾循环。

**粘滞计数的引用计数**（Reference Counting with Sticky Counts）是具有追踪备用的引用计数的扩展。选择一个值 $\xi - 1$，引用计数在此处"粘滞"，不再被进一步递增或递减。这通常是为了将对象头部必须分配的引用计数字段缩减为几个位。

当执行追踪时，它重新计算所有的引用计数。那些曾被粘滞但现在引用数少于 $\xi - 1$ 的活对象将具有正确的计数，而死对象（包括那些曾被粘滞的对象和属于垃圾循环的对象）将具有计数 0。

### 5.2 不动点形式化

在方程 (1) 中，我们将垃圾回收表述为一种抽象的不动点计算。追踪计算最小不动点，而引用计数计算最大不动点。因此，**这两个解之间的集合差构成了循环垃圾 $V_C$**。

在最小不动点（追踪）和最大不动点（引用计数）之间可能存在其他不动点解。如果 $V_C$ 中有 $n$ 个非平凡强连通分量，那么根据图的拓扑结构，不动点方程的解将介于 $n$ 到 $2^n$ 个之间。

找到循环垃圾的一般方法是找到一个节点子集 $S \subseteq V$，使得：

$$
(S \cap R = \emptyset) \land \{(x, y) \in E : y \in S \land x \in V - S\} = \emptyset \tag{3}
$$

也就是说，$S$ 是一个不包含根、仅包含内部引用的集合。因此，存在一个不动点解，其中对于 $s \in S$，$\rho(s) = 0$，从而 $S$ 是垃圾。

循环回收过程的困难问题在于如何选择集合 $S$。

### 5.3 试探删除的引用计数

现在考虑通过试探删除（trial deletion）而非备用追踪回收器来回收循环的引用计数。

在试探删除中，我们从一个可疑的节点 $x$ 开始（怀疑它是垃圾循环的一部分），考察集合 $S = x^{\star}$——从 $x$ 可达的所有节点的集合。如果 $x$ 是循环的一部分，那么循环中的所有节点都从 $x$ 可达。因此，循环是 $x^{\star}$ 的子集。我们递减内部引用计数以得到每个节点的外部引用计数。如果发现任何节点的外部引用计数大于零，我们将其从集合中移除，并恢复其所有子节点的引用计数，因为该节点此时已处于集合外部。我们重复此过程，直到集合中不再有外部引用计数非零的节点。如果集合非空，我们就找到了一个垃圾节点集。

还有一个问题是如何选择启动试探删除过程的节点 $x$。例如，Bacon 和 Rajan 的算法 [^6] 生成完整的候选集（如果对所有候选执行试探删除，则所有循环垃圾都将被找到），同时采用多种启发式方法来减少候选数。

算法维护一个 $P$ 集合，即"紫色"顶点——那些可能是循环垃圾根的顶点。当顶点的引用计数被递减时变为紫色；当其引用计数被递增时不再为紫色。在回收时，引用计数非零的紫色顶点被视为循环垃圾的潜在根。然后执行试探删除，集合 $S$ 表示那些已被标记为"灰色"或被算法访问过的顶点。最后，如果试探删除产生了一个引用计数为零的顶点区域，这些顶点将被 `sweep()` 回收。否则，引用计数被恢复。

## 6. 多堆回收器

到目前为止，我们讨论了全堆和分代垃圾回收系统。现在将我们的分析扩展到多堆（multiple heaps），这些堆可以是非对称的（如分代系统中）或对称的。多堆垃圾回收由 Bishop [^10] 首创，目的是允许高效回收远超物理内存大小的超大堆。

多堆系统通常通过将堆分区，以独立回收某些区域。好处包括减少暂停时间和通过优先回收活对象少的区域来提高回收器效率。

追踪与引用计数的对偶性、其向多堆的扩展，以及循环回收的方法，共同构成了一个智识框架。在这个框架中，我们可以理解基本设计决策之间的相互关系及其算法性质。

### 6.1 引用计数的无处不在

众所周知，引用计数是根本增量的，而追踪不是。然而，我们主张，**任何独立回收某个对象子集的算法，从根本上都在使用引用计数**。

引用计数允许在不咨询其他对象的情况下回收对象 $x$。类似地，增量回收算法允许在不咨询某些其他对象集合 $Y$ 的情况下回收一组对象 $X$。（这里我们指的是通过清除堆的一个明确定义部分来增量回收堆的那类回收器。）因此，唯一的问题是引用计数执行的粒度。我们使用通用术语**宏节点**（macro-node）来指代作为回收单元的典型对象集合。

我们已经看到，记忆集是一种类似引用计数的抽象。因此，分代回收器为堆到新生区的引用维护引用计数。然而，也存在从新生区到堆的引用计数，尽管它是隐式的。通过将新生区和成熟空间视为两个宏节点，存在一条从新生区到成熟空间的宏节点边。换言之，成熟空间宏节点的引用计数至少为 1，即使有来自根集的边也是如此。这意味着成熟空间不能独立于新生区被回收。相反，我们必须首先回收新生区并将所有活对象移入堆中（此时新生区宏节点消失，成熟空间宏节点的计数归零）。或者，我们可以通过暂时将它们视为单个宏节点来执行堆和新生区的统一回收。合并宏节点消除了宏节点边，这是明智的，因为它们内部边类型都属于追踪的范畴。宏节点边汇总了这样一个事实：两个宏节点的组成对象之间可能存在边。

从根本上说，回收循环有两种方法：(1) 将所有对象移动到单个堆中并追踪它，或 (2) 执行试探删除算法，其中循环垃圾被（逻辑上）移入单个区域，该区域随后被整体丢弃。将循环的参与者移入单个堆并不意味着只能有一个这样的堆。例如，可能可以通过静态或动态地对对象进行分区来避免此类引用。

### 6.2 对象重定位

多堆回收器将对象分组成宏节点（不同称谓有：window、car、train、region、increment 和 belt）。为了执行回收，这些算法将对象从一个宏节点复制到另一个。

然而，尽管引用计数可以用来检测对象是活的（或死的），但直接指针在不遍历整个堆的情况下，会阻碍对象重定位。间接指针允许重定位，但无需记忆集的空间代价，而需要付出间接访问的运行时代价，以及间接对象本身及其可能产生的碎片的空间代价。读屏障技术通常将每个对象视为其自身的间接对象，除非它已经被移动。这提供了灵活性，但以读屏障执行为代价，并且仍然受到间接对象引起的碎片的影响。

记忆集是允许重定位的另一种方法。它们避免了读屏障的运行时开销，同时允许增量重定位和压缩，但对象重定位和来自其记忆集的指针更新必须原子地执行，这限制了增量性的水平。特别地，当存在对一个对象的许多引用时，记忆集会遇到**热门对象问题**（popular object problem）。记忆集的空间代价很高，因为有许多入向指针；而增量性很差，因为必须在单个原子步骤中更新任意数量的指针。

### 6.3 Train 算法

Hudson 和 Moss 设计了一种垃圾回收算法，后来被称为 Train 算法 [^25]。Seligmann 和 Garup 发现并修复了该算法的一个小缺陷并实现了它 [^37]。

Train 算法的主要目的是减少与成熟对象空间（MOS）回收相关的暂停时间。假设 Train 是一个分代系统：存在一个新生区，它保留最近创建的对象，并在回收时提升存活的对象。

Train 算法将成熟对象空间划分为固定大小的 car。

  <img src="gc/images/bacon-fig12.jpg" loading="lazy" alt="图 12：Train 算法结构示意图">
  <figcaption>图 12：Train 算法结构示意图</figcaption>
</figure>

在 MOS 的回收过程中，每次回收一个 car——使得 train 算法在 car 的级别上是增量的。因此暂停时间要求决定了 car 的大小。car 被组织成可变大小的 train。car 在 train 内以及 train 之间都是有序的。当一个对象从新生区移动到 MOS 时，通常被移到第一个 train 的末尾，或者如果第一个 train 正在被回收中，则移到第二个 train。

回收始终在第一个 train 上进行。如果没有指向第一个 train 的外部指针（来自根或其他 train），那么 train 中的所有对象都是垃圾，整个 train 被回收。否则，检查第一个 train 的第一个 car。如果没有入向指针（在记忆集中），那么该 car 可以被回收。如果有仅来自同一 train 中后续 car 的指针指向某些对象，那么这些对象被移动到指向它们的最后一个 car 中，或者如果最后一个 car 空间不足，则移入任意更晚的 car。必要时，为该对象创建一个新的 car。

如果存在来自后续 train 的指针，那么对象被移到一个更晚的 train。最佳选择是将其移到有指向该对象的指针的最后一个 train。如果存在从 MOS 外部（即从新生区）指向该对象的指针，则该对象被移到更晚的 train。对当前 car 中所有具有外部指针的对象执行完此操作后，该 car 中将没有任何外部指针，因此剩余的任何对象都是垃圾，整个 car 可以被回收。对第一个 train 中的所有 car 执行完此操作后，指向该 train 的所有外部指针都将消失，整个 train 可以被回收。

为此，算法维护记忆集，记录来自同一 train 中后续 car、来自后续 train 中的对象、以及来自 MOS 外部的指向每个 car 中对象的指针。来自更早 train 和更早 car 的指针无需记忆，因为它们将在该 car 被回收之前被回收。

#### 6.3.1 Train 作为混合体

现在从我们的角度来考虑 Train 算法。显然，它具有追踪成分，因为每个 car 内部都执行追踪。然而，由于存在记忆集来处理跨 car 引用，它也具有引用计数成分。

Train 算法还有一个有趣的特征，即某些引用计数是通过位置编码的：指向同一 train 中后续 car 和后续 train 中 car 的指针不被记录在记忆集中。每个 car 可以被视为聚合对象的超节点（supernode），而 train 则是 car 的超节点。宏节点计数由从早到晚 car（同一 train 内）和从早到晚 train 之间的链接诱导。

与分代情况一样，宏节点边直接反映在 train 算法中。例如，处于首位的 train 作为整体可以被回收，因为在处理完所有 car 之后没有根引用或记忆集引用，而且第一个 train 的宏节点计数为零。

#### 6.3.2 Train 算法中的循环回收

Train 算法中的混合性格外明显，因为它遭受了引用计数的基本问题之一，即循环回收。Train 算法对 car 内循环处理良好，因为 car 通过追踪回收。但跨 car 和跨 train 循环可能导致严重问题。但这并不奇怪，因为这些正是在宏节点层面上的循环，而在该层面使用的是引用计数而非追踪。

在多堆回收器中，例如 train 算法，我们使用相同的步骤。对于 train 中的每个节点，我们维护一个来自后续 train 中的节点指向它的指针列表（记忆集）。我们回收 train 序列中的第一个 train。如果列表中没有指针，也没有来自根的指针，那么该 train 中的节点集满足方程 (3) 的条件，因此可以被回收。因此，我们可以将 train 中的节点集视为我们在 5.2 节讨论中的 $S$。来自后续 train 的指针列表可以视为对 $S$ 的外部引用计数的度量。

然而，如果 train 1 中的节点 $x$ 被 train $n$ 中的节点 $y$ 所指向，那么我们将 $x$ 移到 train $n$。这从 train $n$ 的角度等同于试探删除，因为从 $y$ 到 $x$ 的指针不再属于任何记忆集。同时，从 train 1 的角度看，它对应于试探删除算法的恢复步骤，因为我们有一个指向 $x$ 的外部指针，因此我们将其从对应于 train 1 的集合中移除。

在我们移除了 train 1 中所有被外部引用的节点之后，剩余的节点是垃圾并被回收。在实际操作中，我们每次回收一个 car，而不是整个 train。但这只是为了限制暂停时间，并不实质改变算法的逻辑。

如果 $x$ 和 $y$ 是垃圾集合 $S$ 的一部分，且 train $n$ 是包含可以到达 $x$ 的节点的最小编号 train，那么集合 $S$ 将在 train $n$ 被回收时被回收。

因此，train 算法和试探删除算法都是找到满足方程 (3) 条件的集合 $S$ 的方法。

### 6.4 Older-First 算法

Stefanović 等人 [^40] 倡导一种回收器，它在最年轻的对象之前清除较老的对象，以便年轻对象更有可能死亡。在极端情况下，他们的 oldest-only 回收器将总是回收最老对象中的某个子集。然而，它会多次复制老的活对象。因此，他们提出了 older-first 回收器，该回收器扫描整个堆，从最老的组到最年轻的组逐组回收对象。

由于扫描的特性，最近分配的对象将在最老对象被重新考虑之前至少被回收一次。由于最老的对象先被回收，这些回收器中的记忆集记录的是从较老区域到较年轻对象的引用，这与传统的分代回收器相反。

### 6.6 日志结构文件系统

考察垃圾回收器的实现如何随操作之间的权衡变化而变化是很有启发的。日志结构文件系统 [^35] 通过将更新的文件系统数据和元数据顺序写入磁盘来实现 Unix 文件系统。Unix 文件系统是一个引用计数的有向无环图（硬链接可以产生无环的交叉边）。

随着文件的覆写，日志中较早的数据变为死数据。为了回收这些数据，需要执行"清理"（垃圾回收）。清理在称为段（segment）的固定大小增量上进行：每次压缩若干段。

然而，系统的性能关键取决于清理算法的质量。为了获得良好的性能，执行第二个层次的引用计数，将段视为宏节点（称为"段使用表"）。此外，记录每个段的年龄。回收器然后尝试清理具有低引用计数的老段——有效地动态选择一个新生区。

这种方法对文件系统是可行的，因为开销足够大从而改变了权衡关系。在日志结构文件系统中，所有指针（inode 号）都被间接引用，以允许 inode 本身随着其变更版本追加到日志中而移动。

因此，无需"修复"来自其他段的指针，也不需要记忆集。此外，"写屏障"在磁盘块操作时执行，因此维护第二个引用计数的额外开销微不足道。

由此我们看到，"显然糟糕"的垃圾回收算法在应用于语言运行时系统以外的领域时可能效果很好。

### 6.7 其他多堆回收器

还有其他分裂堆的依据。Shuf 等人将具有高产率类型的对象与非高产率类型的对象分开分配 [^38]。使用优化来减少两个区域之间记忆集的开销。它类似于分布式算法，其中没有宏节点边。

基于连通性的算法使用静态分析来消除写屏障，从而无需记忆集 [^24]。取而代之的是，宏节点和宏节点边在线计算以形成宏节点 DAG。每当需要回收特定的宏节点时，其所有（传递）前驱必须同时被回收。

Blackburn 等人的 Beltway 回收器概括了各种复制回收器，包括追踪回收器、分代追踪回收器和 older-first 回收器 [^11]。与 Train 算法类似，有两个层次：belt（类似于 train）和 increment（类似于 car）。然而，同一 belt 的 increment 之间的宏节点边遵循 older-first 回收器中的顺序。由于这种顺序，存在循环垃圾的潜在问题，通过规定最老的 belt 由单个（可能很大）increment 组成来解决。此外，除了退化的最老 belt 之外，belt 不是宏节点，因为 belt 从不会作为整体被丢弃。

## 7. 成本分析

对每种回收器，我们在一个统一的框架中分析其成本。这允许精确比较每种算法的优劣势，结合给定的存储可用性和应用特征。我们分析每次回收的成本 $\kappa$、回收的频率 $\phi$，以及垃圾回收器施加的总成本 $\tau$，包括回收本身和插入到 mutator 中的回收器代码（如写屏障）。

一般而言，我们对 mutator 做出稳态假设：特别是，假设分配率和堆中垃圾的比例是常数。这自然是不现实的假设，但它们允许我们用合理数量的变量来量化回收器，并为比较不同回收器的特征提供了一个坚实的基础。

### 7.1 成本要素

我们分析每种回收器的成本，包括常数因子。但我们不指定每个参数的系数，因为这会使公式变得笨重。读者应注意，这些是具有隐式系数的真实成本，而非"大 O"记号。

回收器 X 的成本由以下五个量刻画：

- $\kappa(X)$：单次垃圾回收所需的时间（秒）；
- $\sigma(X)$：回收器元数据的空间开销（以 $m$ 为单位）；
- $\phi(X)$：回收频率（赫兹）；
- $\mu(X)$：变更开销（占应用程序运行时间的比例）；
- $\tau(X)$：回收的总时间开销。如果一个程序独立运行需要 1 秒，且 $\tau(X) = 0.5$，则使用回收器 X 运行同一程序需要 1.5 秒。

### 7.2 回收器无关参数

为分析回收器性能，定义以下附加术语：

- $m$：每个对象的（固定）大小（以字为单位）。
- $\mathcal{M}$：内存大小（以 $m$ 字对象为单位）。
- $\omega$：对象大小（以位为单位），$\omega' = \omega / m$ 是字大小（以位为单位）。
- $a$：分配率（对象/秒）。
- $\epsilon$：指针密度，即每个对象中非空指针的平均数量。
- $\mu_R$：根变更率（写入/秒）。
- $\mu_E$：边变更率（写入/秒）。

对于集合和多集合，我们使用手写体字母表示基数。例如 $\mathcal{V}_L = |V_L|$ 是活顶点数。注意，虽然活顶点集 $V_L$ 始终与回收器无关，但总顶点数 $V$ 和死顶点数 $V_D$ 都与回收器有关。对于回收器 X：

$$
\mathcal{V}(X) = \mathcal{M} - \sigma(X) \tag{4}
$$

回收后可用空闲内存为：

$$
\mathcal{V}_D(X) = \mathcal{V}(X) - \mathcal{V}_L \tag{5}
$$

此外，由于假设指针密度为 $\epsilon$，可知 $\mathcal{E}_L = \epsilon \mathcal{V}_L$ 且 $\mathcal{E}_D(X) = \epsilon \mathcal{V}_D(X)$。

### 7.3 总时间

回收的总时间成本一般为：

$$
\tau(X) = \phi(X) \kappa(X) + \mu(X). \tag{6}
$$

我们将抽象组件操作通过一个带有隐式系数的 n 元线性函数转换为时间，记为 $\mathcal{L}(\ldots)$。

### 7.4 统一堆回收器

我们从简单的追踪和引用计数算法的成本分析开始，然后考察各种统一堆混合算法。

### 7.5 T：追踪

我们首先讨论简单追踪垃圾回收算法的空间和时间成本；这些公式构成了后续基于追踪的回收器分析的基础。

#### 7.5.1 遍历栈空间

追踪回收有两个基本的空间开销来源：标记位和用于对象图递归遍历的栈。虽然存在指针反转（pointer reversal）技术 [^36] 可以消除后者的开销，但这是一种显著的空间-时间权衡，因为它意味着更多的写入和遍历。在本文中，为避免成本模型过度膨胀，我们假设不使用指针反转，同时指出它是一种可选方案。

遍历栈的空间成本与对象图的深度成正比。由于长链式结构的存在，这通常被视为问题所在。然而，我们认为通过一些具有尾递归消除性质的简单优化，遍历深度可以大幅降低，且代价很小。

考虑以下代码（图 15）。`mark(obj)` 函数被稍作修改，使其参数已知为非空且未标记。遍历 `obj` 引用对象的循环将遇到的第一个指向未标记对象的非空指针存储在变量 `cdr` 中。如果发现更多非空未标记引用对象，则 `mark(p)` 调用递归处理它们，消耗另一个栈帧。

然而，如果最多只有一个非空未标记引用对象，则不会发生递归。该函数要么在没有非空未标记引用对象时返回，要么在恰好有一个时通过尾递归消除来处理 `cdr` 指针。

```

    do {

        Object cdr ← null;

            if (p ≠ null && ¬ p.isMarked())
                if (cdr == null)
                    cdr ← p;
                else
                    mark(p);
        
        obj ← cdr;
    } while (obj ≠ null);
}

因此，单链表和双链表的递归深度都将为 1：单链表因为只有一个引用对象，双链表因为两个引用对象之一保证已被标记。

据此我们定义：

- $\mathcal{D}'$ 为回收时对象图的遍历深度，即施加上述优化后遍历活对象图所需的递归栈深度。

标记阶段的空间成本将与 $\mathcal{D}'$ 成正比。在支持内部指针（interior pointers）的系统中，空间仅为 $\mathcal{D}'$ 个指针。在不支持内部指针的系统中，指向正在遍历对象的"游标"必须单独维护。因此遍历栈的空间成本 $\mathcal{D}$（以对象为单位测量）为：

$$
\mathcal{D} = \frac{\mathcal{D}'}{m} \tag{7}
$$

或者，在不支持内部指针的系统中：

$$
\mathcal{D} = \frac{\mathcal{D}'}{m} \cdot \left(1 + \frac{\lceil \log_2 m \rceil}{\omega}\right) \tag{8}
$$

对于数据结构为树状的程序，遍历深度将是对数级别而非线性级别。对于更通用的图结构，深度较难预测。由于 $\mathcal{D}$ 通常不可预测，且不希望为遍历栈预留 $\nu(T)$ 个字，大多数回收器实际上使用固定大小的预分配遍历栈。当栈溢出时，使用替代方法。虽然指针反转在渐近意义上更优，但在实践中更倾向于使用简单的 $O(n^2)$ 算法——当递归栈溢出时仅重新扫描堆。

#### 7.5.2 通用空间公式

我们给出一个通用的空间开销公式，可适用于包括追踪在内的多种回收器。

我们通用地假设需要 $b$ 位用于"引用计数"。若 $b = 1$，则为标记位；若 $b = \omega'$，则为完整的字计数；若 $1 < b < \omega'$，则代表这两者之间的权衡。

对于某个使用每对象 $b$ 位、遍历栈深度为 $\mathcal{D}$ 的回收器 X，所需空间为：

$$
\begin{aligned}
\sigma(X) &= \mathcal{D} + \frac{b \mathcal{V}(X)}{\omega} \\

\mathcal{V}(X) &= \mathcal{M} - \sigma(X) \\
&= \mathcal{M} - \mathcal{D} - \frac{b \mathcal{V}(X)}{\omega} \\
&= \frac{\mathcal{M} - \mathcal{D}}{1 + \frac{b}{\omega}}
\end{aligned}
\tag{9}
$$

$$
\sigma(X) =
\frac{\mathcal{D} + \frac{b}{\omega}\mathcal{M}}
{1 + \frac{b}{\omega}}
\tag{10}
$$

#### 7.5.3 追踪回收器的空间成本

对于优化为每对象使用单个标记位的追踪回收器，$b = 1$，公式简化为：

$$
\mathcal{V}(T) = \frac{\mathcal{M} - \mathcal{D}}{1 + \frac{1}{\omega}} \tag{11}
$$

$$
\sigma(T) = \frac{\mathcal{D} + \frac{\mathcal{M}}{\omega}}{1 + \frac{1}{\omega}} \tag{12}
$$

在字长 $\omega' = 32$ 且固定对象大小 $m = 2$（如 Lisp cons 单元）的机器上，$\omega = 64$，因此我们可以近似认为所需空间为每个可能对象的 1 位（仿佛根本不存在元数据），加上递归栈空间。注意我们隐含地假设 $\mathcal{M} \gg \mathcal{D}$。

$$
\mathcal{V}(T) \simeq \mathcal{M} - \mathcal{D} \tag{13}
$$

$$
\sigma(T) \simeq \frac{\mathcal{M}}{\omega} + \mathcal{D} \tag{14}
$$

#### 7.5.4 时间成本

每次回收的成本与根集大小、检查的顶点数和遍历的边数（标记阶段）以及顶点总数（清除阶段）成正比：

$$
\kappa(T) = \mathcal{L}_T(\mathcal{R}, \mathcal{V}_L, \mathcal{E}_L, \mathcal{V}(T)) \tag{15}
$$

当已回收的单元被耗尽时必须执行一次回收，因此回收频率（次/秒）为：

$$
\begin{aligned}
\phi(T) &= \frac{a}{V_D(T)} \\
        &\simeq \frac{a}{\mathcal{M} - \mathcal{D} - \mathcal{V}_L} \tag{16}
\end{aligned}
$$

此处使用了方程 13 的近似。因此总回收成本为：

$$
\begin{aligned}
\tau(T) &= \phi(T) \cdot \kappa(T) \\
        &\simeq \frac{a}{\mathcal{M} - \mathcal{D} - \mathcal{V}_L} \mathcal{L}_T(\mathcal{R}, \mathcal{V}_L, \mathcal{E}_L, \mathcal{V}(T)) \tag{17}
\end{aligned}
$$

### 7.6 C：引用计数

我们现在为引用计数及其衍生回收器建立空间和时间成本函数。

#### 7.6.1 空间成本

虽然引用计数不执行追踪，但当对象的引用计数降为零时，它确实执行递归删除。两者在原则上没有区别，因此递归遍历消耗的空间量似乎相同。

然而，通过使用 Weizenbaum 的非递归释放方法 [^42]，遍历栈的空间可以被消除，代价是将释放推迟到下一次分配。

事实上，存在一种更简单的"指针穿线"（pointer threading）变体，可以在不消耗任何额外内存或缓存读写操作的情况下，高效且即时地遍历死对象栈。据我们所知，这项技术此前未被发表。

递归删除意味着我们从中递归的对象已经被识别为死对象；因此，我们不需要保留其中包含的数据值，只需要保留尚未被遍历的指针。能够使用死对象中的空间是这项技术的关键。

当递归遍历对象图以递减引用计数并释放那些 $\rho = 0$ 的对象时，每个栈帧中有两个基本信息：一个指向正在被回收的对象；另一个标识最近处理了哪个字段。当我们首次递归时，对象中显然至少有一个指针，并且由于我们正在遍历它，我们不再需要它。因此，我们可以在那个被释放的指针单元中存储一个指向父对象的指针。并且由于我们已经知道该对象的引用计数（为零），我们可以用指示当前正在遍历哪个指针的字段来覆写引用计数。

引用计数字段必须足够大以计数对象中的全部指针数，因为它们可能全部指向其他某个（被引用计数的）对象。因此，我们可以保证任何可能导致递归的对象都有足够的空间来存储递归删除所需的"栈帧"。

此外，这项技术不需要读取或写入任何额外的缓存行——每个对象的第一个缓存行本来就必须被检查以执行存储回收。

然而，与追踪不同，引用计数字段不能被优化为单个位：它占据一个完整的字（使用粘滞计数可以放宽这一假设）。

$$
\mathcal{V}(C) = \frac{\mathcal{M}}{1 + \frac{1}{m}} = \frac{m \mathcal{M}}{m + 1} \tag{18}
$$

$$
\sigma(C) = \frac{\mathcal{M}}{m + 1} \tag{19}
$$

也就是说，空间开销为每个对象一个字，这使有效对象大小增加 1 个字，正是将 $b = \omega'$ 和 $\mathcal{D} = 0$ 代入方程 9 和 10 所得的结果。

#### 7.6.2 时间成本

每次回收的成本为：

$$
\kappa(C) = \mathcal{L}_{C_1}(\mathcal{V}_D(C), \mathcal{E}_D(C)) \tag{20}
$$

即识别死顶点的成本。回收频率与追踪相同：

$$
\phi(C) = \frac{a}{\mathcal{V}_D(C)} \tag{21}
$$

#### 7.6.3 变更成本

引用计数跳过了追踪执行的初始化步骤，但将写屏障插入代码中。因此，总成本必须包含变更率，对于朴素引用计数而言与 $\mu_R$ 和 $\mu_E$ 成正比：

$$
\mu(C) = \mathcal{L}_{C_2}(\mu_R, \mu_E) \tag{22}
$$

因此在无循环的情况下，引用计数的总成本为：

$$
\begin{aligned}
\tau(C) &= \phi(C) \cdot \kappa(C) + \mu(C) \\
        &= \frac{a}{\frac{m\mathcal{M}}{m+1} - \mathcal{V}_L} \mathcal{L}_{C_1}(\mathcal{V}_D(C), \mathcal{E}_D(C)) + \mathcal{L}_{C_2}(\mu_R, \mu_E) \tag{23}
\end{aligned}
$$

### 7.7 CT：引用计数 + 追踪备用

现在考虑第 5.1 节描述的、周期性地使用追踪回收器来回收循环垃圾的引用计数回收器。

#### 7.7.1 空间成本

在 CT 算法中，每个对象拥有一个引用计数，且追踪部分需要递归遍历的空间。因此 CT 的空间成本为：

$$
\mathcal{V}(CT) = \frac{\mathcal{M} - \mathcal{D}}{1 + \frac{1}{m}} \tag{24}
$$

$$
\sigma(CT) = \frac{\mathcal{M} + \mathcal{D}}{1 + \frac{1}{m}} \tag{25}
$$

#### 7.7.2 时间成本

为评估循环回收的性能，定义：

- $c \leq a$，循环垃圾的生成率。

为计算回收器的总成本，我们必须计算引用计数和追踪两方面的成本。我们从追踪回收的角度来考察，因为这些回收定期发生（且频率较低）。这导致更简单的分析；如果试图从引用计数部分的角度评估成本，模型会变得复杂——因为每次连续回收释放的内存越来越少，导致回收频率随时间递增，直到执行追踪回收。

从追踪回收器的角度来看，可以将引用计数回收器视为一个"新生区"回收器，它降低了进入追踪回收器"成熟空间"的分配率。具体而言，虽然应用程序以速率 $a$ 分配数据，但系统仅以速率 $c$ 为追踪回收器创建数据，因为除循环垃圾外的所有垃圾都被引用计数回收器回收。因此，追踪回收的频率为：

$$
\phi(CT) = \frac{c}{\mathcal{V}_D(CT)} \tag{26}
$$

追踪回收本身的成本不变：

$$
\kappa(CT_T) = \kappa(T) = \mathcal{L}_T(\mathcal{R}, \mathcal{E}_L, \mathcal{V}_L, \mathcal{V}(CT)) \tag{27}
$$

为分析引用计数的成本，我们将其视为以连续增量方式运行。追踪回收间隔为 $\mathcal{V}_D / c$ 秒，期间分配 $\frac{\mathcal{V}_D}{c} a$ 个单元。其中 $\mathcal{V}_D$ 个未被引用计数释放（因为它们是循环垃圾）。因此在两次追踪回收之间被引用计数释放的单元数为：

$$
a \frac{\mathcal{V}_D}{c} - \mathcal{V}_D = \left(\frac{a}{c} - 1\right) \mathcal{V}_D
$$

假设指针密度均匀，对于每个顶点 $v$，我们遍历 $\mathcal{E}_D / \mathcal{V}_D$ 条指针，共 $\mathcal{E}_D$ 条指针。因此每个"追踪周期"的引用计数成本为：

$$
\kappa(CT_C) = \left(\frac{a}{c} - 1\right) \cdot \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D) \tag{28}
$$

综合上述结果，得到带追踪备用的引用计数的总成本：

$$
\begin{aligned}
\tau(CT) &= \mathcal{L}_{C_2}(\mu_R, \mu_E) + \phi(CT) \cdot (\kappa(CT_T) + \kappa(CT_C)) \\
        &= \mathcal{L}_{C_2}(\mu_R, \mu_E) + \frac{a}{\mathcal{V}_D} \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D) + \\
        &\quad \frac{c}{\mathcal{V}_D} (\mathcal{L}_T(\mathcal{R}, \mathcal{V}_L, \mathcal{E}_L, \mathcal{V}(CT)) - \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D)) \tag{29}
\end{aligned}
$$

当没有循环垃圾时（$c = 0$），最后一项消失，$\tau(CT) = \tau(C)$。

### 7.8 CD：延迟引用计数

延迟引用计数（第 4.1 节）将考虑根的代价从应用程序转移到回收器。因此，回收成本变为：

$$
\kappa(CD) = \mathcal{L}_{CD}(\mathcal{R}) + \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D) \tag{30}
$$

回收频率与追踪和引用计数相同：

$$
\phi(CD) = \phi(C) = \frac{a}{\mathcal{V}_D} \tag{31}
$$

因此总回收成本为：

$$
\begin{aligned}
\tau(CD) &= \phi(CD) \cdot \kappa(CD) + \mathcal{L}_{C_2}(0, \mu_E) \\
        &= \frac{a}{\mathcal{V}_D} (\mathcal{L}_{CD}(\mathcal{R}) + \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D)) + \mathcal{L}_{C_2}(0, \mu_E) \tag{32}
\end{aligned}
$$

#### 7.8.1 空间成本

延迟引用计数的空间成本是引用计数成本加上零计数表（ZCT）占用的空间。一般情况下，ZCT 的表项数可以达到系统中活对象和死对象的总数。因此，健壮的实现使用每个对象中的一个位来指示它是否在 ZCT 中。总成本是引用计数空间加上 ZCT "存在位"的空间：

$$
\begin{aligned}
\sigma(CD) &= \frac{\mathcal{V}}{\omega} + \frac{\mathcal{V} \lceil \log_2 \mathcal{V} \rceil}{\omega} \\
           &= \frac{\mathcal{V}}{\omega} \cdot (1 + \lceil \log_2 \mathcal{V} \rceil) \tag{33}
\end{aligned}
$$

### 7.9 CC：引用计数 + 试探删除

现在考虑通过试探删除（第 5.3 节）而非备用追踪回收器来回收循环的引用计数。

该算法的成本是基本引用计数算法的成本加上试探删除循环的额外工作。然而，试探删除也会应用于活子图的某一部分，这部分成本也必须计入。我们引入参数：

- $\lambda$，被试探删除算法检查的活顶点 $V_L$ 的比例（$0 \leq \lambda \leq 1$）。

为计算回收成本，我们使用与 CT 算法相同的方法：将试探删除阶段 $CC_D$ 视为"主导"阶段，并以该阶段的周期来描述回收。

试探删除阶段在所有空闲内存被循环垃圾耗尽时被调用：

$$
\phi(CC) = \phi(CT) = \frac{c}{\mathcal{V}_D} \tag{34}
$$

试探删除算法的成本是两次遍历所有循环垃圾（在此情况下即全部 $V_D$）加上对活子图的遍历：

$$
\kappa(CC_D) = \mathcal{L}_{CC_D}(\mathcal{V}_D + \lambda \mathcal{V}_L, \mathcal{E}_D + \lambda \mathcal{E}_L) \tag{35}
$$

关于非循环垃圾的引用计数回收的时间成本与 CT 算法相同：

$$
\kappa(CC_C) = \kappa(CT_C) = \left(\frac{a}{c} - 1\right) \cdot \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D) \tag{36}
$$

因此 CC 回收器的总成本为：

$$
\begin{aligned}
\tau(CC) &= \phi(CC) \cdot (\kappa(CC_D) + \kappa(CC_C)) + \mathcal{L}_{C_2}(\mu_R, \mu_E) \\
        &= \mathcal{L}_{C_2}(\mu_R, \mu_E) + \frac{a}{\mathcal{V}_D} \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D) + \\
        &\quad \frac{c}{\mathcal{V}_D} (\mathcal{L}_{CC_D}(\mathcal{V}_D, \lambda \mathcal{V}_L, \mathcal{E}_D, \lambda \mathcal{E}_L) - \mathcal{L}_{C_1}(\mathcal{V}_D, \mathcal{E}_D)) \tag{37}
\end{aligned}
$$

#### 7.9.1 空间成本

引用计数加循环回收的空间成本是引用计数成本加上紫色集合 $P$ 占用的空间加上每对象颜色信息（在抽象算法中以集合 $Y$ 表示）的成本。令 $\pi$ 为紫色节点的比例，则空间成本为：

$$
\sigma(CC) = \mathcal{V}(CC) \left(\frac{\lceil \log_2 \mathcal{V}(CC) \rceil}{\omega} + \frac{1}{\omega} + \frac{\pi}{m}\right) \tag{38}
$$

### 7.10 分裂堆回收器

我们用以下量来刻画分裂堆回收器：

- $N \subset V$ 是新生区（nursery）。
- $H = \overline{N}$ 是成熟空间堆（mature space heap）。
- $V_{NL}$ 和 $E_{NL}$ 分别是新生区中的活顶点集和活边集。
- $V_{ND}$ 和 $E_{ND}$ 分别是新生区中的死顶点集和死边集。
- $V_{HL}$、$E_{HL}$、$V_{HD}$ 和 $E_{HD}$ 是成熟空间堆中的对应集合。

### 7.11 GT：追踪式分代回收

现在考虑第 4.3.1 节描述的标准追踪分代回收器。我们假设一个简单的分代回收器，其中新生区大小固定，对象在经受一次新生区回收后即被移入成熟空间。本节中"堆"一词作为"成熟空间"的同义词使用。

回收新生区时，我们从根 $R$ 和从成熟空间到新生区的根 $R'$ 开始在新生区内向前追踪。之后清空新生区。成本为：

$$
\kappa(GT_N) = \mathcal{L}_T(\mathcal{R} + \mathcal{R}', \mathcal{V}_{NL}, \mathcal{E}_{NL}, \mathcal{N}) \tag{39}
$$

新生区回收频率为：

$$
\phi(GT_N) = \frac{a}{\mathcal{N}} \tag{40}
$$

成熟根集的大小最多可达 $V_H$，下文将进一步讨论。

回收成熟堆就如同执行一次简单的追踪回收。成本为：

$$
\kappa(GT_H) = \mathcal{L}_T(\mathcal{R}, \mathcal{V}_{HL}, \mathcal{E}_{HL}, \mathcal{H}) \tag{41}
$$

新生区的使用削弱了进入堆的分配率。最终堆分配率为 $a \frac{\mathcal{V}_{NL}}{\mathcal{N}}$。因此堆回收频率为：

$$
\phi(GT_H) = \frac{a \frac{\mathcal{V}_{NL}}{\mathcal{N}}}{\mathcal{V}_{HD}} \tag{42}
$$

分代回收的总成本是新生区回收、堆回收和写屏障成本之和：

$$
\begin{aligned}
\tau(GT) &= \phi(GT_N) \cdot \kappa(GT_N) + \phi(GT_H) \cdot \kappa(GT_H) + \mathcal{L}_{GT}(\mu_E) \\
        &= \frac{a}{\mathcal{N}} \cdot \mathcal{L}_T(\mathcal{R} + \mathcal{R}', \mathcal{V}_{NL}, \mathcal{E}_{NL}, \mathcal{N}) + \\
        &\quad \frac{a \frac{\mathcal{V}_{NL}}{\mathcal{N}}}{\mathcal{V}_{HD}} \cdot \mathcal{L}_T(\mathcal{R}, \mathcal{V}_{HL}, \mathcal{E}_{HL}, \mathcal{H}) + \mathcal{L}_{GT}(\mu_E) \tag{43}
\end{aligned}
$$

#### 7.11.1 空间成本

与对应的非分代版本类似，标记位和遍历深度有空间成本。此外，如果记忆集以顺序存储缓冲区（即修改对象列表）的方式维护，且连续两次回收之间成熟空间中的每个对象都被修改，则它可能占用 $V_H$ 的空间。空间开销等于追踪回收器的开销加上记忆集：

$$
\sigma(GT) = \mathcal{D} + V / \omega
$$

### 7.12 GCH：追踪新生区 + 引用计数堆

现在考虑一个新生区被追踪、堆被引用计数的分代回收器（第 4.3.3 节）。新生区的成本和频率与 GT 算法相同。堆回收的频率也相同。堆回收的成本是应用于堆的延迟引用计数的成本。

$$
\kappa(GCH_N) = \kappa(GT_N) \tag{44}
$$

$$
\phi(GCH_N) = \phi(GT_N) = \frac{a}{\mathcal{N}} \tag{45}
$$

$$
\kappa(GCH_H) = \mathcal{L}_{CD}(\mathcal{R}) + \mathcal{L}_{C_1}(\mathcal{V}_{HD}(GCH), \mathcal{E}_{HD}(GCH)) \tag{46}
$$

$$
\phi(GCH_H) = \phi(GT_H) = \frac{a \frac{\mathcal{V}_{NL}}{\mathcal{N}}}{\mathcal{V}_{HD}(GCH)} \tag{47}
$$

$$
\tau(GCH) = \phi(GCH_N) \cdot \kappa(GCH_N) + \phi(GCH_H) \cdot \kappa(GCH_H) + \mathcal{L}_{GT}(\mu_{E_H}) \tag{48}
$$

## 8. 空间-时间权衡

到目前为止，我们一直考虑每种回收器的唯一规范实现。当然，有许多实现决策会改变性能特征。然而，几乎所有这些都是某种空间-时间权衡，一旦选择了基本的回收器设计，就可以应用于各个内存区域。

### 8.1 复制回收器

复制回收器通过分配一个额外的半空间并将活数据复制到新的半空间来用空间换时间。因此，它们省去了标记-清除式回收器所需的遍历死数据的 $\mathcal{V}$ 迭代（图 3 中的 `sweep-for-tracing()` 函数），但付出了等量的 $\mathcal{V}/2$ 空间代价。

### 8.2 记忆集

虽然分代回收器中的记忆集可能包含成熟空间中的所有对象，但这是极不可能的。预分配这种状况的空间是过度的超额配置。相反，可以动态地从成熟空间和新生区借用记忆集的空间。最好从成熟空间借用。如果变更率够低使得借用的空间不会耗尽，新生区回收频率不受影响。另一种方案是，从新生区借用空间将一定会增加新生区回收的频率为：

$$
\phi(GT_N) = a / (N - \Omega) \tag{49}
$$

其中 $\Omega$ 是新生区中为记忆集分配的空间量。这种技术通过利用变更率通常不高的假设，以空间换时间。

也可以考虑位图或卡片标记方法，其中开销被大幅降低——分别降低 $w$ 倍或卡片大小 $k$ 倍。前一种情况不损失精度，但写屏障必须执行位更新。卡片标记的写屏障代码更短更快，但精度损失（一张卡片对应多个对象）将导致垃圾回收期间更长的扫描时间。

对于基于槽位的位图，空间开销降至：

$$
\sigma(GT) = \mathcal{D} + V / \omega + V_H / \omega \tag{50}
$$

对于卡片标记，空间开销更小：

$$
\sigma(GT) = \mathcal{D} + V / \omega + V_H / k \tag{51}
$$

其中 $k$ 为卡片大小。

### 8.3 遍历

对于追踪回收器，重建函数中的递归遍历需要栈空间 $\mathcal{D}$。这可以通过使用指针反转 [^36] 以额外一次遍历活对象 $\mathcal{V}_L$ 的代价完全消除。然而，这通常是一个糟糕的权衡，因为实践中栈深度远小于活对象的数量（$\mathcal{D} \ll \mathcal{V}_L$）。

更好的策略是使用固定大小的递归栈，然后在栈溢出时使用某种技术来处理。要么回退到指针反转，要么丢弃栈并开始从左向右扫描堆以找到未标记的对象。后一种方法虽然实现更简单，也是并发系统中更自然的实现，但其复杂度是 $O(n^2)$。

## 9. 结论

我们证明了追踪和引用计数垃圾回收——先前被认为截然不同——事实上共享完全相同的基本结构，可以视为彼此的对偶。

这反过来使我们能够证明，所有高性能垃圾回收器实际上都是追踪和引用计数技术的混合体。这解释了为什么高度优化的追踪和引用计数回收器具有惊人相似的性能特征。

在此过程中，我们发现了一些有趣的事情：写屏障本质上是引用计数的特征；循环的存在使得垃圾回收本质上是非增量的：**循环回收是"类追踪"的**。

我们还以回收器无关和回收器相关的量的形式提供了各类回收器的成本度量。这些成本度量不会"作弊"——例如忽略回收器元数据的空间成本。因此，它们允许直接进行"头对头"的比较。

回收器的设计可以变得更加系统化。在构建回收器时，需要做三个决策：

1. **分区**：将内存（堆、栈和全局变量）划分为一组分区，在每个分区中可以应用不同的策略；
2. **遍历**：对于每个分区，决定通过追踪还是引用计数来遍历对象图；
3. **权衡**：对于每个分区，选择空间-时间权衡，例如半空间 vs. 滑动压缩、指针反转 vs. 栈遍历等。

我们的统一垃圾回收模型使我们能够系统地理解和探索垃圾回收器的设计空间，并为选择与相关应用特征匹配的垃圾回收器提供了一种更具原则性的方法。

未来，这一方法论可能有助于实现根据特定应用特征动态构建的垃圾回收算法。
